# cert9.db / mid-session reading breakage — статус расследования

Снимок на 2026-08-31. Это рабочая заметка для возобновления работы, не часть продукта — не коммитить в trunk без необходимости.

## Ветки
- `trunk` — продакшн. Сейчас там: `tools/thunderbird-cert-cleanup` v0.5.0 (компоуз-триггер + shutdown-триггер), DLL v0.4.3 (PID/version-теги в логах + fallback-пересбор в `manager.rs`, см. ниже — этот фикс НЕ решает проблему чтения, оставлен как есть).
- `experiment/cert-cleanup-mid-session` — тестовая ветка для add-on'а. Там собраны версии v0.4.1–v0.4.18 (эксперименты: reload/logout PKCS11-модуля, dbkey-lookup, synth-sign-encrypt через `nsIMsgComposeSecure`, compose-window-trigger).

## Установленные факты (НЕ требуют повторной проверки)
1. Постоянное наличие дубликата сертификата (без приватного ключа) в `cert9.db` ломает чтение зашифрованной почты; перезапуск Thunderbird не чинит, пока дубликат физически не удалён.
2. **`nsIX509CertDB.getCerts()` САМА ПО СЕБЕ, без единого обращения к файлу/cert9.db, ломает расшифровку** до перезапуска или до отправки нового зашифрованного письма. Подтверждено контрольной сборкой v0.4.10.
3. Точечный `certDB.findCertByDBKey(dbKey)` (не только широкий `getCerts()`) **тоже** ломает чтение (v0.4.14) — то есть проблема не в конкретном API, а в ЛЮБОМ обращении к `nsIX509CertDB` из WebExtension Experiment.
4. Полный, успешный синтетический sign+encrypt через `nsIMsgComposeSecure` (v0.4.17, тот же API, что и реальная отправка) НЕ чинит и не предотвращает поломку чтения.
5. PKCS11-module reload / token logout — не удалось получить чистый воспроизводимый тест (API нестабилен между сборками Thunderbird Daily), тупик, заброшено.
6. Реальная ОТПРАВКА письма (полный цикл через compose window) чтение чинит — воспроизводимо, надёжно.
7. Механизм поломки живёт в Gecko/PSM выше NSS (не в самой NSS/softoken — проверено на чистой сборке NSS из исходников, поломка не воспроизводится) и не в нашем PKCS11-модуле (RUST_LOG показывает, что реальные вызовы декрипта у нас либо вообще не случаются, либо успешны).
8. **Корневая причина на уровне Gecko C++ не найдена и, по всей видимости, требует живой отладки на Windows (Process Monitor / ETW), которой сейчас нет.**

## Что проверено и ОТБРОШЕНО в этой сессии (не переисследовать)
- `ThreadId(2)`-строки в логе — не от нашего процесса/сборки, не отслежен источник, признано нерелевантным шумом.
- `CKO_NSS_TRUST` (trust-мост для Windows root CA, добавлен 25 августа, commit `5c6fc4a`) — **работает правильно**, я ошибочно прочитал лог и решил, что он всегда пуст; при аккуратной перепроверке поиск для `office-CA01-CA` находит trust-объект 20/20 раз. НЕ баг.
- Гипотеза "список объектов модуля протухает между `C_OpenSession`" (v0.4.3, fallback-пересбор в `manager.rs::start_search`) — целилась в CKO_NSS_TRUST-проблему, которой не существует. Фикс сам по себе безвреден, но не решает проблему чтения. Есть в trunk, можно оставить или откатить — не критично.
- Идея "продублировать `msgHdrViewSMIMEOverlay.js`-баг → значит это причина всего" — НЕТ, это отдельный, самостоятельный баг Thunderbird (см. ниже), не объясняет корень.
- Идея "0 deleted → значит cleanup не виноват" — ОШИБКА: `doCleanup()` всегда вызывает `certDB.getCerts()` первым шагом, независимо от того, находит ли он что-то для удаления. Per факт №2, этого одного вызова достаточно для поломки. "0 deleted" ничего не доказывает и не опровергает.

## Отдельная, реальная находка (не связана с корневой причиной, но стоит зарепортить)
`encryptionStatus()` в `mail/extensions/smime/content/msgHdrViewSMIMEOverlay.js` (comm-central) при `aEncryptionStatus != SUCCESS` пытается показать страницу ошибки через `btoa()` с локализованными (рус/укр) строками `CantDecryptTitle`/`CantDecryptBody`. `btoa()` не умеет в кириллицу → `Uncaught DOMException: String contains an invalid character` → окно письма остаётся пустым вместо нормального сообщения об ошибке. Связано с более ранним черновиком бага на Bugzilla (см. историю этой же сессии, тема btoa()/Cyrillic). Стоит зарепортить отдельно — облегчит диагностику любых будущих S/MIME-сбоев для пользователей с нелатинской локалью, не только для этой ситуации.

## Развилка, которая уже была сделана пользователем в этой сессии
Выбор между:
- **v0.4.0-стиль (только при выходе)**: без побочных эффектов в сессии, но дубликат (и П1 — тихая поломка подписи) может копиться весь день до перезапуска.
- **v0.5.0 (компоуз-триггер + shutdown)**: чинит подпись прямо перед отправкой, ценой временной поломки чтения других писем до момента отправки (самовосстанавливается).

Пользователь сознательно выбрал v0.5.0, отправлено в `trunk`. Ничего, найденное в этой сессии, не даёт технической возможности избавиться от этого трейд-оффа без глубокой Windows-отладки (Process Monitor/ETW), которой у меня нет удалённо.

## Обновление: v0.4.19 (before-send-trigger) — попробовали и ОТБРОШЕНО
Идея: вместо триггера на открытие compose-окна (v0.5.0/v0.4.18) — запускать cleanup в `browser.compose.onBeforeSend` (async listener ожидается перед реальной отправкой), чтобы окно поломки схлопнулось до долей секунды перед send, раз send надёжно чинит чтение.

**Результат — хуже, а не лучше.** После отправки ПЕРВОГО ЖЕ письма чтение сломалось и **осталось сломанным до перезапуска Thunderbird** — тот же самый send, который в v0.5.0 надёжно чинил чтение, здесь этого не сделал. То есть склейка cleanup вплотную перед send не просто не помогает — она ломает саму способность send восстанавливать состояние (вероятно, getCerts() в этот момент топчет какой-то кэш резолюции сертификата получателя/identity, который send обычно успевает построить заново за то время, что окно письма было открыто).

**Вывод: не пытаться склеивать cleanup с моментом отправки.** v0.5.0 (триггер на открытие окна, отдельно от send) остаётся лучшим из проверенных вариантов — самовосстановление через send в нём работает надёжно.

## Обновление: v0.4.24 (send-button-trigger) — тоже ОТБРОШЕНО, подтверждает паттерн
Та же идея, что и v0.4.19, но технически надёжнее: id-based перехват `command`-события на самой кнопке/пунктах меню "Отправить" (`button-send`/`cmd_sendButton`, `menu-item-send-now`/`cmd_sendNow`, `cmd_sendLater`), на **capture**-фазе — то есть наш listener гарантированно срабатывает раньше, чем Thunderbird начинает обработку своей команды отправки (`goDoCommand`/`GenericSendMessage`).

**Результат — тот же отрицательный паттерн, что и v0.4.19.** Реальный дубликат найден и удалён (`1 deleted`), но чтение сломалось и **не самовосстановилось через саму отправку** — потребовался полный перезапуск Thunderbird, как и раньше.

**Вывод (подтверждён дважды независимо, двумя разными техническими механизмами):** дело не в точности тайминга относительно отправки (async listener vs synchronous capture-phase event) — САМА БЛИЗОСТЬ к моменту отправки вредна. Самовосстановление через send работает **только** если между нашим разрушением состояния (cleanup) и реальной отправкой проходит целая compose-сессия (пользователь печатает получателя и т.д.) — то есть между разрушением и "чинящим" событием должна быть НЕ близость по времени, а достаточно НОРМАЛЬНОЙ активности Thunderbird с сертификатами (естественные резолвы через `asyncFindCertByEmailAddr` и т.п.), которая успевает произойти. Триггер на открытие окна (v0.5.0) даёт этому время; любой триггер рядом с самой отправкой — нет.

**Вся ветка экспериментов с позицией триггера теперь исчерпана и закрыта:**
- compose-window-open (v0.4.18/v0.5.0) — работает, самовосстанавливается.
- compose.onBeforeSend (v0.4.19) — не восстанавливается, нужен перезапуск.
- sign-checkbox toggle (v0.4.20-23) — использовался только для отладки самой техники перехвата, не как финальный кандидат.
- send-button command-event на capture-фазе (v0.4.24) — не восстанавливается, нужен перезапуск.

## Обновление: v0.4.25 (on-send-error-trigger) — новое направление, не тайминг, а условие
Пользователь предложил не гонять cleanup ПРЕВЕНТИВНО (на каждое открытие окна/отправку — то есть и тогда, когда дубликата нет вообще), а РЕАКТИВНО — только когда `browser.compose.onAfterSend` репортует реальную ошибку отправки (`sendInfo.error` не пусто). Логика: чинить всё равно придётся с тем же побочным эффектом (поломка чтения до перезапуска, судя по паттерну), но частота срабатывания падает с "каждое письмо" до "только когда баг с дубликатом реально проявился" — что, по описанию исходной проблемы (П1), происходит относительно редко.

`implementation.js` заметно упрощён — весь privileged DOM-хук на compose-окно убран, триггер теперь простой `browser.compose.onAfterSend`-listener в `background.js` (не требует Experiment-хуков вообще, только `"compose"` permission).

**Компромисс:** нельзя "починить" именно то письмо, которое упало — cleanup срабатывает уже post-factum, пользователю нужно вручную повторить отправку. Но резко падает ЧАСТОТА побочного эффекта.

Тест ещё не проведён на момент записи.

## Обновление: v0.4.25 отброшен, v0.4.26/27 — новая попытка того же реактивного подхода
`browser.compose.onAfterSend` (v0.4.25) **структурно не может увидеть** ошибку `finishCryptoEncapsulation` — подтверждено по исходникам comm-central (`MsgComposeCommands.js`, `CompleteGenericSendMessage`): при ошибке код делает `return` из catch-блока ДО строки `window.dispatchEvent(new CustomEvent("aftersend"))`, на которой построен `onAfterSend`. Не баг тайминга — это в принципе недостижимый путь для этого класса ошибок.

Заменили на `nsIMsgComposeStateListener` (`nsIMsgCompose.idl`), регистрируется через `gMsgCompose.RegisterStateListener()` — тот же официальный API, которым пользуется сам Thunderbird. `ComposeProcessDone(aResult)` получает реальный nsresult, минуя внутренний try/catch.

v0.4.26 не сработал: `gMsgCompose` ещё не существует на событии `load` окна (подтверждено собственным диагностическим логом). v0.4.27 добавляет поллинг (100мс, до 5 сек) вместо однократной проверки.

## v0.4.27 подтверждён рабочим + новая находка пользователя (ключевая!)
Поллинг `gMsgCompose` сработал, `ComposeProcessDone` ловит ошибку корректно.

Пользователь протестировал 3 сценария после ошибки отправки (дубликат в cert9.db):
1. Ошибка → OK → **сразу повторная отправка** (не пытаясь читать письма) → письмо уходит, **чтение остаётся рабочим**.
2. Ошибка → OK → **сначала попробовать читать письма** → чтение ломается.
3. Из сломанного состояния (после 2) → повторная отправка → письмо уходит, но **чтение НЕ восстанавливается**.

Вывод: разрушение состояния (`getCerts()`) происходит в обоих случаях, но самовосстановление через реальную отправку срабатывает, только если отправка происходит СРАЗУ, до того как пользователь успел понаблюдать сломанное состояние (не пытался читать). Это тот же паттерн, что и у v0.5.0 (открытие окна → пользователь печатает получателя → отправка чинит), просто сжатый во времени.

## v0.4.28 — автоматизация рабочего сценария (auto-retry)
Реализовано:
- Авто-закрытие модального диалога ошибки (`chrome://global/content/commonDialog.xhtml`, id `commonDialogWindow`, матчинг по `.opener` — устанавливается `Services.ww.openWindow`) через уже существующий `domwindowopened`-observer.
- Отслеживание последнего `msgType` через лёгкую обёртку `GenericSendMessage` (только запись аргумента, поведение не меняется).
- `ComposeProcessDone` при ошибке: cleanup → автоматический повторный вызов `GenericSendMessage(lastMsgType)`.
- Защита от зацикливания: флаг `__certCleanupRetrying`, если повтор тоже упал — не повторяем снова, просто логируем и сдаёмся.

**Не протестировано на момент записи.** Риски, за которыми надо следить в логе: (а) реально ли закрывается диалог и не блокирует ли поток дальше; (б) не уходит ли письмо ДВАЖДY (если наш `close()` диалога срабатывает уже ПОСЛЕ того, как что-то успело продолжиться); (в) нет ли зацикливания повторов.

## Найден и исправлен баг после публикации v0.6.0: двойная регистрация listener'а
После того как v0.6.0 ушёл в trunk, пользователь заметил на тестовой ветке (v0.4.28): на ВТОРОМ письме, где произошёл реальный сбой, срабатывала защита от зацикливания — cleanup не запускался вообще.

Причина по логу: `registered nsIMsgComposeStateListener 2` (консоль схлопнула 2 одинаковые строки) — listener регистрировался на одном окне ДВАЖДЫ, поэтому `ComposeProcessDone` срабатывал дважды на один реальный сбой. Старый флаг `__certCleanupRetrying` не отличал "это дубликат исходного сбоя" от "это реально retry, и он упал" — видел `true` и сдавался, а флаг мог застревать в неправильном состоянии, молча блокируя cleanup для следующего письма.

**Исправлено в v0.4.29** (`experiment/cert-cleanup-mid-session`):
1. `registerStateListener` сам защищён от повторной регистрации на одном окне (независимая проверка, не полагается только на `hookComposeWindow`'s guard).
2. Флаг `__certCleanupHandling` (переименован) теперь ВСЕГДА сбрасывается на любом выходе — не может застрять навсегда.

**Нужно перенести этот фикс в `trunk` (v0.6.0 → v0.6.1)**, как только пользователь подтвердит, что v0.4.29 работает чисто на нескольких письмах подряд.

## Подтверждено: v0.4.29 (дедуп-фикс) работает — 2 цикла подряд прошли чисто, письмо ушло со 2-й попытки, зацикливания нет.

## ВАЖНАЯ НОВАЯ НАХОДКА: самовосстановление работает только ОДИН РАЗ за сессию
Пользователь протестировал 3 письма подряд:
- Письмо 1: сбой подписи (старый дубликат) → cleanup нашёл и удалил → auto-retry → **успех, чтение НЕ сломалось**.
- Письмо 2: ушло с первой попытки без ошибок (но, по словам пользователя, **дубликат создаётся при КАЖДОЙ отправке** — это и есть механизм исходного бага П1: NSS кэширует подписанта при любой проверенной подписи, включая свои отправленные письма).
- Письмо 3: сбой подписи (новый дубликат от письма 2) → cleanup нашёл и удалил (это ВТОРОЕ срабатывание удаления за сессию) → auto-retry → письмо ушло, **но чтение сломалось и осталось сломанным до перезапуска**.

**Вывод: у самовосстановления через немедленный повтор отправки, похоже, есть ограничение — оно надёжно работает только на ПЕРВОЕ срабатывание cleanup+retry за сессию Thunderbird. Второе и последующие срабатывания (даже с разными письмами, не подряд по времени) уже не самовосстанавливаются.**

Это не решено и, скорее всего, не может быть решено дальнейшим перебором вариантов кода — упирается в тот же нерешённый вопрос "что именно портится в Gecko C++ выше NSS", для которого ещё раньше в этой сессии был сделан вывод: нужна живая отладка на Windows (Process Monitor/ETW), которой нет в текущем окружении.

Также важно: раз дубликат создаётся при каждой отправке (не только при явном сбое), значит auto-retry триггер потенциально будет срабатывать чаще, чем предполагалось при разработке v0.6.0 ("редкие случаи, когда баг проявился") — возможно на каждое повторное успешное+неуспешное чередование в сессии.

## Статус: в проде с известным ограничением
v0.6.0 (`trunk`) остаётся лучшим найденным компромиссом — реже ломает чтение, чем v0.5.0, и чинит подпись автоматически. Но полной гарантии самовосстановления в сессии с несколькими срабатываниями нет — задокументировать это как известное ограничение. Дальнейшая доработка v0.4.29-фикса (дедуп regsitration) в `trunk` как v0.6.1 остаётся актуальной задачей (сам фикс подтверждён рабочим, просто выявилось ДОПОЛНИТЕЛЬНОЕ, более глубокое ограничение поверх него).

Ветка `experiment/cert-cleanup-mid-session` содержит полную историю всех опробованных вариантов триггера — полезно для будущих сессий.

## Обновление 2026-09-01: v0.6.0 "proactive triggers" — новая архитектура, собрана и выложена, ЕЩЁ НЕ ПРОТЕСТИРОВАНА
Пользователь предложил (после того как v0.5.5 подтвердил: таймер чинится, отложенный reinit срабатывает с успехом дважды, но чтение всё равно ломается) полностью убрать реактивный retry и заменить тремя независимыми проактивными триггерами:
1. Открытие нового compose-окна → безусловный `reinitCertVerifier()` (без чтения/удаления cert9.db).
2. Клик по кнопке/пункту меню "Отправить", перехват на capture-фазе ДО реальной отправки → `doCleanup()` (поиск+удаление дубликата, БЕЗ reinit), затем оригинальная отправка проходит ровно один раз.
3. Выход → `doCleanup()` (без reinit — процесс всё равно завершается).

Вся реактивная цепочка (`ComposeProcessDone`, `recreateComposeSecure()`, wrap `GenericSendMessage`, авто-retry) убрана полностью — ни одно окно больше не вызывает `BeginCryptoEncapsulation()` дважды, так что баг с дублированием `mCerts`/RecipientInfo структурно недостижим независимо от состояния чтения.

**ВАЖНО, было прямо озвучено пользователю перед сборкой:** триггер 2 сам по себе (cleanup вплотную к отправке, без reinit, расчёт на самоисцеление через сам send) — это ТОЧНО тот же механизм, что уже дважды проваливался выше (v0.4.19, v0.4.24): находил и удалял дубликат, отправка проходила, но чтение ломалось и НЕ самовосстанавливалось через сам send, требовался полный перезапуск. Единственное новое здесь — триггер 1 (reinit при открытии окна, задолго до отправки), который в такой комбинации с триггером 2 раньше не тестировался. Пользователь решил: собрать и протестировать как есть, без добавления reinit в триггер 2.

Собрано, выложено: тег `tools-cert-cleanup-v0.6.0-proactive-triggers`, https://github.com/AnatoliChe/osclientcerts/releases/download/tools-cert-cleanup-v0.6.0-proactive-triggers/cert-cleanup.xpi. `updates.json` на ветке `experiment/cert-cleanup-mid-session` обновлён.

**Следующий шаг: дождаться реального теста пользователя.** Если чтение ломается и не самоисцеляется (повторяя паттерн v0.4.19/v0.4.24) — это будет означать, что даже проактивный reinit-при-открытии-окна недостаточен для защиты близкого-к-отправке cleanup, и придётся либо (а) добавить reinit сразу после cleanup в триггере 2 (перед реальной отправкой), либо (б) вернуться к формуле "cleanup только при открытии окна, задолго до отправки" (как v0.5.0), которая по крайней мере надёжно самоисцелялась через сам send.
